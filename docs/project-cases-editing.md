# 개인 프로젝트 사례 편집

`data/project-cases.json`에는 GPU CCWS·SWL, HexaHarness, DRAM ATLAS 세 사례만 있다. 세 카드 모두 보이고 과정·배울 점·한계는 선택해서 펼친다. 점수나 순위를 표시하지 않는다. 원강의·필수 실습과 분리한 선택 읽기이며 기존 배울 점과 실습 내용은 유지한다.

## 자료 경계

상위 조사에서 확인한 프로젝트만 사례로 넣는다. 최근 프로젝트 몇 개를 전체 작업 이력처럼 소개하지 않는다. 원 세션·회사 자료·개인정보·비밀·원로그·절대 경로·내부 URL·세션 ID를 이 배포 폴더에 복사하지 않는다. 근거 대조 기록과 비식별화 판단은 저장소 밖 작업 보고서에 보관한다. 교재에는 확인된 내용을 짧게 요약한 텍스트만 넣는다.

`outcome`에는 실제 확인한 결과를 적는다. 설계 의도·제안·미실행 계획을 성과로 바꾸지 않는다. 실측 근거가 없는 시간·비용·성능 향상 수치는 넣지 않는다. 미확인 범위는 `limits`에 남긴다. 프로젝트 이름·분야·기간도 확인한 정보만 사용하며 기간은 생략할 수 있다.

## 데이터 형식

최상위 필드는 `version: 1`, `cases: [...]` 두 개다. 배포 데이터에는 정확히 세 사례만 넣는다. 제외한 조사 자료는 저장소 밖 로컬에 보관하며 숨긴 카드·JS 데이터·배포 ZIP에 남기지 않는다. 사례마다 아래 필드를 사용한다. 실제 사례처럼 보일 수 있는 샘플은 배포 데이터에 넣지 않는다.

| 필드 | 내용 |
|---|---|
| `id` | 중복 없는 소문자 영문·숫자·하이픈, 60자 이내 |
| `title` | 비식별 사례 제목, 100자 이내 |
| `summary` | 목록에서 읽을 문제와 선택의 요약, 300자 이내 |
| `category` | 연구·검증 / 도구·자동화 / 교육·콘텐츠 / 제품·사용경험 중 하나 |
| `tags` | 연결 개념 1~4개, 각 30자 이내. 예: 역할 분담·근거 확인·인계 |
| `period` | 선택. 확인된 기간만 60자 이내 |
| `context` | 어떤 상황에서 시작했나, 600자 이내 |
| `approach` | 실제로 어떻게 진행했나, 600자 이내 |
| `outcome` | 확인된 결과, 400자 이내 |
| `lesson` | 다른 프로젝트에 가져갈 판단, 600자 이내 |
| `limits` | 한계·실행하지 않은 것·확인하지 못한 효과, 400자 이내 |
| `evidence_status` | 당시 근거 상태와 미확인 범위, 200자 이내 |
| `transfer` | AI DRAM Wiki에 옮길 원칙. 적용 제안임을 명시, 600자 이내 |
| `review` | `evidence_checked: true`, `privacy_checked: true`, `checked_on: YYYY-MM-DD` |

모든 텍스트는 HTML로 실행하지 않고 이스케이프한다. 임의 필드, 빈 값, 중복 ID·태그, 유효하지 않은 날짜와 미완료 검토 상태는 빌드에서 거부한다. 검토 플래그는 사람이 실제 검토를 마친 뒤 입력하는 기록이며, 개인정보나 근거를 자동 판정했다는 증거가 아니다.

## 미리보기와 게시 전 확인

`python3 build.py`는 확인된 사례가 없는 동안에도 명시적인 준비 중 화면을 만들어 로컬 UI를 확인할 수 있게 한다.

게시 전에는 다음 명령을 반드시 사용한다.

```sh
python3 build.py --require-project-cases
```

사례 수가 세 개가 아니거나 검토를 마치지 않았으면 출력 파일을 쓰기 전에 중단한다. 사례가 있어도 원문 대조·비식별화 검토를 대신하지 않으며, 배포 권한도 이 옵션이 부여하지 않는다.

검색·필터·더 보기 제어는 사용하지 않는다. 각 사례의 상세 내용은 브라우저 기본 `details`로 접어 두어 키보드·터치로 펼칠 수 있다. 현재는 로컬 준비만 승인됐으며 빌드 성공은 게시 승인이 아니다.
